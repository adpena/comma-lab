Two things make this load-bearing. First, the legs agree to **0.36%** while their crossing counts

## 2. SG2-2a — the actuator's target set is not the scored set

`gt_n600_sR.npz::sR` is the cached through-R fragility-weighted **input** sensitivity
`S_R(i) = |∂(Σ_p w_p·margin_p)/∂x_i|`, `w = exp(−margin/τ)`, τ = 0.5
(`tools/precompute_sR_reachability.py`). It is the map of *where our render error has leverage*.

**Caveat carried on every sR number, in the direction it biases:** the cached array is
`clip(S_R / percentile(S_R, 99), 0, 1)` — per-frame normalized and **clipped**, with the top 1%
saturated (measured saturated fraction **0.010000**, exactly as designed) and the per-frame
absolute scale unrecoverable. Clipping removes tail mass, so **every concentration number and
every ceiling below is a LOWER BOUND.**

### 2.2 What this means, stated carefully

**The tilt is real but small, and it is FLAT.** Every bucket from margin 0 to margin 2 carries the
same 2.60–2.73× leverage ratio. Leverage does *not* keep concentrating as margin → 0. So
`S_R` carries essentially one bit beyond "near a boundary or not," and the trainer's default
saliency `exp(−margin/τ)` — which falls by e⁻⁴ ≈ 0.018 across that same band — is **sharper than
the measured leverage justifies.**

**74.911% of the leverage sits on pixels that can never flip.** This is *not* waste in pb3's sense.
S_R is an input-side quantity: a pixel deep inside a class still moves nearby boundary margins
through the receptive field (halo 685, 23 global SE blocks — `ddm_tl1` §2.3). The correct reading
is that **the actuator's accuracy requirement is spread over essentially the whole frame with only
a 2.7× tilt**, while the *scored* set is 0.42% of it. The 238× sparsity is an output-side fact and
buys the actuator nothing.

### 2.3 The saliency ceiling, at its most favourable reading

The 2.713× figure is the tilt toward the *flip-capable* set. A saliency lever would target the
*most-leveraged* pixels instead, which is more favourable. From the measured Lorenz curve

## 3. SG2-2b — is there a free SUBSPACE? (my hypothesis, and its refutation)

§2's flatness has an obvious alternative explanation: if the free directions were **frequencies**
rather than **locations**, a pixel-space map like `sR` would look flat *by construction*. The
contest path is a resample, so this was the strong hypothesis. It is wrong, and the measurement
that kills it is exact.

**Method.** Both `interpolate` modes are separable, so each operator factors as a tensor product of
two small 1-D matrices, each built EXACTLY by pushing unit impulses through the very same torch
calls production uses. Separability was **verified before any spectrum was reported**, with a
working negative control: true-vs-factored max relative error **4.31e-16**, while a deliberately
wrong factorization returns **0.1238** — the probe can return the negative (`m50`).

### 3.1 `R_lin` — the training-side render→render round trip

`R_lin = bilinear_down(874×1164 → 384×512) ∘ bicubic_up(384×512 → 874×1164)`, both
`align_corners=False`; this is `precompute_sR_reachability._R_torch` minus the clamp/round, which
is identity under the uint8-STE used everywhere in training.

| quantity | value |
|---|---:|
| σ_2d range | **[0.686643, 1.028266]** |
| σ_2d median | 0.881272 |
| **condition number** | **1.4975** |
| modes with σ < 0.5 | **0** (also 0 below 0.25, 0.1, 0.03, 0.01, 0.003, 0.001) |
| white-error energy survival | 78.39% |

**REFUTED.** `R_lin` has no null space and no near-null space; the most-attenuated mode loses only
1.46×. In hindsight the reason is structural and should have been predicted: *up*-then-*down* with
the intermediate resolution **higher** than both ends is a resampling round-trip, and bicubic
interpolation is exact at the original nodes. Nothing is thrown away, so nothing is free.

### 3.2 `D` — the operator our SHIPPED error actually crosses

I measured the wrong operator first. `inflate.py` writes **camera-resolution** frames; the scorer's
own `preprocess_input` then resizes to 384×512 (`upstream/modules.py:73,109`,
`mode='bilinear'`, `align_corners=False`, `antialias=False`). So the map from our shipped per-pixel
error to anything SegNet can see is `D`, a genuine **dimension reduction**.

| quantity | value |
|---|---:|
| dim camera → dim scorer | 1,017,336 → 196,608 |
| rank | 196,608 (full row rank) |
| **null-space dimension** | **820,728 = 80.674%** |
| exactly-unsampled camera px | **230,904 = 22.696926%** |
| σ_2d range (row space) | [0.500022, 0.993511] |
| **condition on row space** | **1.9869** |
| white-error energy survival | **8.589%** (amplitude 29.31%) |

The unsampled-pixel count **reproduces the landed
`ADVISORY_evaluator_video_geometry_20260710.md` figure (230,904 / 22.6969261%) exactly**, derived
here as the identically-zero columns of an independently-constructed matrix. That is an
independent corroboration of `m86` and a validation of my construction.

### 3.3 What the big null space is and is not — and an exact structural closure

**80.674% of shipped-error directions are exactly invisible to SegNet.** Moving error *into*
Null(D) cannot lower d_seg, for the reason that makes the space large: `Dδ = 0` means the scorer's
input is unchanged, so d_seg is unchanged *by construction*. As a place to **hide** error it is
seg-free capacity (room to carry pose or save rate), never a d_seg lever.

**But it is exactly the slack that makes the uint8 preimage problem SOLVABLE**, and that is a
different and real use. `ddm_ll1`'s window solve does not hide error in Null(D); it *spends*
Null(D)'s freedom to make `D(f1_cam)` hit the intended render exactly, driving realization error to
≈0 (88 flips → 3, `ΔS = −0.01441`, n = 3). §6.

**Exact closure between the two derivations.** `ddm_ll1` derives the geometry combinatorially:
because both downsample strides exceed 2 (874/384 = 2.2760, 1164/512 = 2.2734) the 2×2 read
windows cannot overlap, so each of the 196,608 scorer pixels owns a **private** 2×2 camera window
with one linear constraint in four integers ⇒ **3 free dimensions per window**, plus the untouched
pixels. That predicts

```
196,608 windows × 3 free dims  +  230,904 untouched px  =  820,728
```

which is **exactly** my SVD's `null_space_dim = 820,728`, to the integer. A continuous
singular-value computation and a combinatorial window count, derived independently by two arms
from two different starting points, agree exactly. Each validates the other.

One more consistency check: the 230,904 exactly-unsampled pixels are coordinate directions inside
Null(D), i.e. the `m86` blind set. `ddm_bp2` tested exactly that set as a *pose* actuator and
measured "does not pay" — consistent: it is free, not powerful.

**The d_seg-relevant number is the spread WITHIN the row space, and it is 1.987×** — so perfect
frequency steering inside the visible subspace, at fixed error energy, is worth
`RMS σ / σ_min = 0.6667 / 0.5000 = ` **1.33×**.

description capacity **across classes, edges and pairs** is byte-neutral and none of them bounds
it. That lever is now priced, because **the coarea estimator decomposes ρ exactly by class edge**:
each crossing carries the unordered class pair it separates, so

`ρ = Σ_{edges {a,b}} ρ_{a,b}` — an **exact additive** decomposition, not an attribution heuristic.

orientation, so a well-measured edge gives ≈1.0 *even when strongly anisotropic*. Road↔MyCar — the
hood line, **20.67×** more horizontal than vertical crossings — returns **1.093**. The three edges
with poor self-tests (0.139, 0.648, 1.777) are precisely the three smallest, together **0.43%** of
ρ, with crossing counts in the hundreds: the self-test correctly flags exactly where it is
unreliable, and it is unreliable only where nothing is at stake.

### 5.1 The density predicts the realized flip distribution — an independent cross-check

|---|---:|---:|---:|
| Road↔Lane | 49.2% | 40.96% | **1.20** |
| Road participates | 87.8% | 89.35% | 0.98 |

**Scope, stated because it matters:** `pc2`'s 458,738 flips corresponds to d_seg 0.003889 — the

indicative, not exact.

Two readings, both useful:

- **Road-participation agrees to 2%.** The geometry of the source margin field, alone, predicts

- **Road↔Lane carries 1.20× more flips than its density share.** Since flips_edge ≈ ρ_edge·r_edge,

## 7. Round-1 adversarial self-review — six attacks, all executed

**A1 — my leading hypothesis was wrong, and I published the refutation.** I predicted the free
directions were frequencies (§3 preamble). The exact spectrum says `R_lin` has condition 1.4975 and
zero attenuated modes. Recorded as a refutation, not quietly dropped. It also caught a real error:
I had measured the **wrong operator** — the training-side `R_lin`, not the shipped-side `D`. §3.2
is the correction.

**A2 — can my separability probe return the negative?** Yes, verified: a deliberately wrong
factorization returns rel-err **0.1238** against **4.31e-16** for the correct one. The spectrum is
only reported when the check passes (the tool `return 2`s otherwise).

**A3 — is my D construction right?** Independently corroborated: 230,904 identically-zero columns =
22.696926%, matching a landed figure derived by a different method. Had I mis-built D (wrong
`align_corners`, wrong `antialias`), this count would not have landed on the known value.

**A4 — am I understating the saliency ceiling?** Initially yes. My first framing quoted only the
**2.713×** tilt toward the flip-capable set. But a saliency lever would target the *most-leveraged*
pixels, not the flip-capable ones — a more favourable and more honest reading, giving **5.17× at
q = 5%**. §2.3 now reports both. The conclusion survives (5.2 < 14.5) but the number was corrected
upward against my own thesis. Separately, the p99 clip makes all of these **lower bounds**, and I
cannot bound how much higher the true value is without the unnormalized S_R — named as owed.

**A5 — is the byte-neutral family actually exhausted?** **No, and I nearly claimed it was.** My
measurements bound only *within-frame* placement. Cross-class / cross-edge / cross-pair allocation
is untouched by them, and `ddm_pc2` shows it is where the mass is. §5 exists because of this
attack; the headline is scoped to "within-frame" throughout. The attack then forced the §5
measurement, which turned an unbounded hand-wave into an exact decomposition.

**A6 — a real bug in my own new code, caught by its own closure test.** The first per-edge
implementation **summed** the x- and y-axis estimators where `coarea_rho` **averages** them. Each
axis is a *complete* estimator of ρ (0.028576 vs 0.028677), so summing double-counts: the edge
total came out at 0.0563 against a coarea ρ of 0.0286, a clean 2×. Caught because I checked
`rho_total_from_edges` against the undecomposed value instead of reporting shares alone — shares
sum to 1 by construction and would have looked perfect while every absolute ρ_edge was 2× wrong.
Fixed to average per axis; the total now closes to **0.02862649 vs 0.028626495**. The per-edge
x/y self-test was added in the same fix so the estimator carries its own validity check per edge.

**What this review did NOT close.** (i) No independent-**producer** anchor for ρ — the coarea test
reads the same array and validates the *mechanism*, not the array (§1.4). (ii) The sR ceilings are
clip-limited lower bounds. (iii) `R_lin`'s spectrum is the STE linearization; a null-space
perturbation can still cross a camera-resolution rounding boundary, so "free" is first-order —
which is exactly the nonlinearity `ddm_ll1` manipulates. (iv) I did not measure our *actual* δ, so
