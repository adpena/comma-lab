## Bug 1 (FIXED) — Lever-C `--pose-dim-weights-auto` crashes on MPS float64

`measure_pose_dim_weights_from_targets(scorer.pose_targets, ...)` called
`torch.as_tensor(pose_targets, dtype=torch.float64)` directly on the scorer's pose
targets, which live on the MPS gradient backend when `--train-device mps`. MPS does not
support float64:
```
TypeError: Cannot convert a MPS Tensor to float64 dtype as the MPS framework
doesn't support float64. Please use float32 instead.
```
This is a real integration bug between `--split-by-head --train-device mps` and
`--pose-dim-weights-auto` — the time-optimal arm_b config hits it on the FIRST measurement
before training starts.

**Fix** (`src/tac/torch_vehicle/pose_dim_weights.py`): detach the targets to CPU before the
double-precision variance measurement (a one-time host-side stat — device-independent):
```python
if torch.is_tensor(pose_targets):
    pose_targets = pose_targets.detach().to("cpu")
t = torch.as_tensor(pose_targets, dtype=torch.float64)
```
Verified: MPS-tensor input now measures correctly (`[0.30,0.30,0.30,1.79,3.00,0.30]`, mean
1.0) both in isolation AND in the live pipeline. +2 regression tests added (one MPS-input,
skipif no-MPS; one requires_grad input). 16/16 tests pass. Self-protects the bug class per
CLAUDE.md "Bugs must be permanently fixed AND self-protected against".

## Finding 2 (for the orchestrator) — eval never fires when `eval_every` > every scaled stage length

Run #1 used `--eval-every 8`. With `--total-epoch-budget 16`, the curriculum scales to stage
lengths `[2,3,1,1,5,1,2,3]` — NO single stage has ≥8 epochs. The eval gate is
`evaluated = (epoch_in_stage % spec.eval_every) == 0` (driver.py:2818) keyed on
`epoch_in_stage` (per-stage, resets each stage), so with eval_every=8 it NEVER becomes True
→ no eval scheduled → `best_score` stays `inf` → no `best/` dir written. The run still
completed cleanly (`skipped_async_evals:0`), it just never produced a best checkpoint.

This is a SMOKE-CONFIG interaction, NOT a production bug: at the full 29,650-epoch budget
the stages have thousands of epochs each and `epoch_in_stage % 8 == 0` fires regularly. But
it is a sharp edge for SMOKES and short tuning runs: the eval cadence must be ≤ the longest
SCALED stage length, else the run produces no eval/best. Run #2 with `--eval-every 2` fires
correctly (eval scheduled at epoch_in_stage==2). Recommendation for smokes: set
`--eval-every` ≤ the shortest stage you want to evaluate within (1 or 2 for tiny budgets),
or have the launcher warn when `eval_every` exceeds every scaled stage length.

## Finding 3 (observation, for the orchestrator) — async-eval at n=600 on CPU is the smoke bottleneck

The CPU authority eval streams the full video over 600 pairs; on this M5 Max each eval ran
~3–4 min. With `--async-eval` it does NOT block training (training kept advancing; the
throttle skips overlapping evals), but it dominates wall-clock for a TINY training budget
(the 18-epoch train is ~2–3 min; one eval is ~3.5 min). For fast smokes, consider a small
`--n-pairs`-independent eval-subset knob (the driver's eval uses the full n; only the
byte-close harness exposes `--max-pairs`). Also: `pose_mse` read flat at 9.4078 across
stages 2–8 in run #1 — likely the APGC adaptive throttle holding pose cadence; worth a
closer look by the orchestrator but not a pipeline failure (pose path is active, finite,
descended from 22.5→9.4 early).

## Finding 4 (for the orchestrator) — `verify_e2e_byte_close_eval.py` does not support FiLM-v2 wrapped checkpoints

The byte-close on the arm_b re-tapered FiLM-v2 EMA shadow succeeded (parity_ok=True), but the
harness then raised at the eval step:
```
RuntimeError: parse-back decoder load mismatch (NO-FAKE):
  missing=['stem.weight', ... , 'rgb_0.weight', 'rgb_1.weight']
  unexpected=['stored_pose', 'decoder.stem.weight', ... , 'pose_mlp.fc1.weight',
              'film_resid.proj.weight', 'film_resid.gamma_head.weight', ...]
```
Root cause: a FiLM-v2 run's EMA shadow (and therefore the production `best/best_ema_decoder.pt`)
is the WRAPPER state-dict — keys are `decoder.*`-prefixed plus extra `pose_mlp.*` /
`film_resid.*` / `stored_pose` tensors. `verify_e2e_byte_close_eval.py::_build_decoder` builds a
BARE `ConfigurableTaperHNeRVDecoder` and `load_state_dict(strict=False)` then errors on the
prefix + extra tensors.

The PRODUCTION path is SOUND — the driver's own `_build_archive_and_eval_decoder` (driver.py:2287)
has a FiLM-v2-aware branch (`pose_film_v2.build_archive_with_pose` / `parse_pose_section` /
`_FiLMEvalDecoder` cursor adapter) that splits the wrapper into the codec decoder blob + the
additive pose section and rebuilds a faithful FiLM-conditioned eval decoder. So in-loop eval +
`best/` archive build work for FiLM-v2. The gap is ONLY in the STANDALONE readiness harness
`verify_e2e_byte_close_eval.py`, which the P3/G3 readiness flow uses to turn a `best/` into an
advisory S on contest hardware.

RECOMMENDATION for the orchestrator: extend `verify_e2e_byte_close_eval.py` to detect a FiLM-v2
wrapped checkpoint (presence of `decoder.`-prefixed keys / `stored_pose` / `film_resid.*`) and
route through `pose_film_v2.build_archive_with_pose` + `_FiLMEvalDecoder` (reuse the driver's
proven code), instead of the bare-decoder path. Until then, the standalone readiness actuator
only covers NON-FiLM checkpoints; the production arm_b run (FiLM-v2 ON) needs the driver's own
byte-close/eval path (which it already runs in-loop) OR the harness extension for the G3 packet.
(I did NOT patch the harness in this P3 unit — it is a non-trivial feature, scoped here as the
P3 finding for the orchestrator to prioritize, per "do LESS but make it REAL".)
