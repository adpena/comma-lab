public cluster that recently moved; VEH/CAP says gt-to-gt receiver capacity is

### 2. Event-Driven Exit Design

Verdict: **ADOPT the exact predicate below; reject hardcoded step stopping.**

Ticket predicate:

```text
N = 120
H = 384
W = 512
eval_every_steps = 50
checkpoint_every_steps = 250
min_eval_rows = 5
window_rows = 5
creep_eps_dseg_per_eval = 1.0e-6
plateau_eps_dseg_per_eval = 5.0e-7
sustained_erosion_windows = 3
forecast_safety_steps = 3250
wall_clock_cap_seconds = ticket_budget_seconds

For every eval row, atomically append:
  step, wall_seconds, loss, lr, d_seg_batch_mlx, best_d_seg_batch_mlx,
  optional cpu_torch_checkpoint_d_seg, checkpoint path, checkpoint sha256.

Define objective_S = 100 * d_seg_batch_mlx.
Define one_sample_flip_S = 100 / (N * H * W).
Define marginal_bar_S_per_step = one_sample_flip_S / eval_every_steps.

After at least min_eval_rows rows, run:
  evaluate_trajectory_stop(
    points=(step, objective_S),
    config=TrajectoryStopConfig(
      score_units_per_objective=1.0,
      marginal_score_gain_per_compute=marginal_bar_S_per_step,
    ),
    safety_bound_compute=forecast_safety_steps,
  )

STOP_CONVERGED iff stop_reason in {converged_projected, marginal_below_bar}
  AND the last window is not DIVERGING_ERASING
  AND any available CPU-torch checkpoint facet agrees within the registered
      MLX schedule/noise envelope.

EXTEND_WITH_RESUME iff stop_reason == continue_projected
  AND wall_clock_cap_seconds or forecast_safety_steps binds
  AND the best checkpoint is still improving or projected tail gain exceeds
      one_sample_flip_S over the next eval interval.

QUEUE_RESUME iff safety_bound_REPORTED or wall-clock cap binds while
  continue_projected is still true. This is a safety stop, not convergence.

ROLLBACK_OR_RETREAT iff the last window has d_seg slope > creep_eps while loss
  slope < 0 for at least sustained_erosion_windows, or CPU-torch facets refute
  the MLX trend beyond the envelope.
```

Falsifier: if the ticket contains a fixed "stop at 3250" terminal rule, or if a
wall-clock/safety cap is written as convergence, the event design is invalid.

### 3. fp16-Train Risk

Verdict: **Use fp16 in the saturated first burn, with fp32/CPU authority gates.**

Evidence: the whole-step saturated bench measured 7.658940 s/step versus
10.420921 baseline, a 1.361x speedup, while d_seg sanity stayed inside the
observed short-bench schedule envelope. The fp16 profiler decomposition is
explicitly instrument-scoped and must not be used as a mechanism claim. The
actual verdict path remains fp32 CPU-torch facets on checkpoints and eventual
exact archive evaluation, not MLX fp16.

Admission rule: the first n120 mem-probe/short-horizon sanity must compare the
saturated path against a fp32 hygiene+cache reference or an already-held fp32
anchor. If the same checkpoint/sample shows fp16 worse by more than 2.0e-6
d_seg or changes the event classification, fall back to fp32 hygiene+cache for
the reference burn. Otherwise keep fp16.

Falsifier: a same-seed n120 short sanity where fp16 flips the stop/continue
decision or violates the 2.0e-6 d_seg guard.

### 4. Renderer-Backward Kernel Timing

Verdict: **After-first-burn or mid-burn; do not delay the first receiver burn.**

WC3 priced the target: renderer backward is 0.442 s of the 0.775 s fp32 chunk
graph, 57% of graph time. It is the right next kernel family, but it is not the
right precondition for the first n120 verdict. The current saturated path is
already the best measured end-to-end route. A kernel landing mid-burn can be
picked up at a checkpoint/resume boundary after parity and whole-step bench
prove it.

Time-to-first-verdict rule:

| Route | First-verdict read |

| Kernel before burn | Wins only if parity, code review, and whole-step bench finish before the seal and show at least 1.25x additional end-to-end n120 speedup. |
| Kernel mid-burn | Preferred: build/test in parallel; adopt only at a checkpoint boundary after exact same-object sanity. |

before the M1 ticket seal finishes, with at least 1.25x additional end-to-end
