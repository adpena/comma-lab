## 0. TL;DR (the verdict up front)

The openpilot seeding is **well-engineered and close to optimal GIVEN the measurements** — the two flagged BLOCKING gaps (#237/#224) are closed, the pose carrier warm-starts from the *superior* prior, and the lane band's FP-killer + dash-gate are sound. **BUT there are 4 concrete suboptimalities, one MEASURED**, and the "one world-model both axes" UNIFICATION is **DESIGNED but deliberately NOT wired as the #205 default — which is CORRECT, not a gap**, because the two measured verdicts (lane ξ-coding REFUTED; PoseNet-target beats openpilot-ego as the pose prior) already tell us the coding-unification is Pareto-dominated. **The real left-on-table d_seg leverage is NOT more unification — it is (1) the MEASURED lane-IPM horizon suboptimality (v_h=174 shipped vs 188 FEED-dj-optimal) that mis-places the dash-gate FP-killer (the 90%-dominant lane residual), and (2) unifying the two divergent ground-plane calibrations.** Ranked recommendations in §3; unification verdict in §4; $0 de-risks in §5.

## 2. THE UNIFICATION — is one world-model exploited across both axes? (the operator's core question)

**The physical claim (real):** ONE ego trajectory `ξ_ego(t)` generates BOTH scored axes — d_pose = the INTRA-pair twist (frame0→frame1), lane advection = the INTER-pair motion (pair t−1→t) — both through the same ground homography (`ego_xi_trajectory.py:12-49`; pose-solved memory "ONE ξ, triple-use"). The seam object (`XiEgoTrajectory`) is built for exactly this.

**Is it exploited? NO in the live trainer — and that is CORRECT, not a gap.** Three independent geometry computations run, sharing source data (`gt.lstars`, `gt.gt_poses`) and fit primitives but NO shared ξ object:
1. pose ξ ← `xi_from_pose_calibration(gt.gt_poses)` (PoseNet-target, its own ξ; does NOT go through the `XiEgoTrajectory` seam).
2. lane φ1 seed ← `build_structured_lane_sdf(gt.lstars[src_pair])` (SDF, one frame).
3. lane render band ← `build_analytic_lane_band_prior(gt.lstars[pi])` (coverage, per-frame, no ξ).

**Why NOT-wiring the unification is the RIGHT call (measured, not lazy):**
- **Lane ξ-coding is REFUTED.** The `advect_slot_matrix` LBND3 predictor (the coding-level unification) measured WORSE than the LBND2 baseline (1.08–1.14×), while ξ-FREE temporal smoothing hit −42% (lane-band-rate-crux memory + `analytic_lane_render_band.py:1263` in-code note). This highway clip is swap-light → the ego-advect has nothing to predict that smoothing doesn't do cheaper. So using ξ to CODE lanes is Pareto-dominated. ✅ correctly OFF.
- **The pose warm-start already uses the SUPERIOR prior.** The memory frames the unification as "openpilot ego-ξ warm-starts pose." But the live carrier warm-starts from the **PoseNet TARGET** (component A) — the exact quantity d_pose matches — which dominates the openpilot-ego prior (only up-to-affine related). So there is nothing to gain by routing pose through the openpilot-ego seam. ✅ already best-in-class.
- **Coherence does NOT lower lane d_seg.** The band is GT-fit per-frame = the oracle shape floor (0.00087); a coherent/smoothed source DEVIATES from GT → RAISES d_seg (the lossy-smoothing cost). So the d_seg band should stay per-frame-GT-fit (or lossless-coherent), which it is. Coherence is a RATE lever, and it's the A/B in §3-R4.

**Conclusion:** the "one world-model both axes" unification is a genuine, elegant DESIGN pattern, but the measurements have already collapsed its two would-be payoffs (lane-rate coding, pose warm-start) — one refuted, one superseded by a better prior. **Exploiting it further is NOT where the d_seg leverage is.** The left-on-table optimality is in the geometry CALIBRATION the three paths independently (and inconsistently) roll (H, D), not in fusing them into one ξ. There is ONE speculative unmeasured d_seg use of ξ — a ξ-driven partition temporal-consistency regularizer (the "third dual-use") — but the measured erasure is spectral-bias/finest-scale (∝1/persistence), already addressed by the persistence-loss + island-amplify levers ON in the config; temporal-consistency is a distant, unmeasured fifth-priority lever, NOT a #205 change.

## 3. RECOMMENDED CHANGES (ranked by expected d_seg/d_pose leverage; all $0 to prepare, none blocks launch)

**R1 — 🟡 MEASURED, HIGHEST leverage: fix the lane-IPM horizon `v_h 174 → 188` (FEED-dj-optimal) and unify `_CAM_H 1.2 → 1.22`.**
- Where: `lane_sdf_component.py:69-70` (and it flows to `analytic_lane_render_band.build_analytic_lane_band_prior` default `v_h=_V_HORIZON`, which the trainer does NOT override — Agent-3 trace `:1650-1652`).
- Deep-math: the horizon is the image-row→forward-meter map. The **dash-gate** (the FP-killer, and the dash-gap FP is 90% of the recon lane d_seg per the analytic-lane memory) gates on `forward < 55 m`. A wrong horizon mis-maps forward-distance → the dash on/off pattern and the 55 m near/far boundary land on the wrong rows → the dominant lane residual is attacked in the wrong place. The in-code note (`:70`) says FEED-dj measured **188** IPM-optimal; the ship value is **174**.
- Action for the config agent: either (a) change the `lane_sdf_component._V_HORIZON` default to 188 after re-confirming FEED-dj through-R at n600, or (b) thread a `--lane-band-v-horizon` flag (currently the trainer cannot override it) and set 188. Unify `_CAM_H` to the openpilot `CAMERA_HEIGHT_M=1.22` used by the pose warp. **This is the single measured-backed d_seg lever in the seeding.**
- Caveat: re-confirm 188 through-R at n600 before pinning (the FEED-dj anchor is a partition-level IPM sweep; verify it holds through R+SegNet). $0 de-risk in §5.

**R2 — 🟡 unify the ground plane to ONE calibrated source (consistency + maintainability; sister of R1).**
- Where: `lane_sdf_component.py:66-70` hardcodes its own intrinsics + plane; `warp_real_luma_frame0.py:85-91` reproduces its own; `calibrated_geometry.py:55-59` is the canonical EON pin but is torch-only and defines NO camera-height-in-meters / road-plane.
- Deep-math: the pose ξ advects frame0 through a ground plane at (cam_h=1.22, pitch=0); the lane band IPMs image rows through a ground plane at (cam_h=1.2, v_h=174). These are **two different physical planes** for the SAME rig → the pose-warped world and the lane-projected world are ~1.6% inconsistent. One calibrated ground plane (cam_h=1.22, the measured horizon, pitch from `liveCalibration`) should serve BOTH.
- Action: add a numpy/MLX-friendly `GroundPlane` (cam_h, pitch, v_horizon) to `calibrated_geometry` (or a shared `boundary_math` constant) and have both `lane_sdf_component` and `warp_real_luma_frame0` import it. Low d_seg leverage on its own; it makes R1 permanent and removes the drift class.

**R3 — 🟡 the lane φ1 seed (F) is single-source-pair + CE-collapsed → either strengthen or accept the render band as the sole lane authority.**
- Where: trainer `:1356-1360` (`_lp_lstar = gt.lstars[src_pair]`, one frame).
- Deep-math: the lane geometry varies per frame (curving road); a single-frame φ1 SDF is a coarse average seed, and it's measured to be washed out by the CE pretrain (`lane_px=0`). The render band (G) is the true per-frame lane authority. Two honest options: (a) DE-EMPHASIZE — accept the φ1 seed is near-inert and lean on the render band (no change; the config already has both ON); (b) STRENGTHEN — build the φ1 seed as a ξ-STABILIZED multi-frame ground-frame consensus (project all frames' class-1 into the ξ-corrected ground frame → ONE coherent world lane model → advect back to `src_pair`). Option (b) IS a legitimate use of the pose ξ for a d_seg seed — but it's UNMEASURED and the seed is measured-weak, so it is a lower-priority experiment than R1. Recommend (a) for #205, (b) as a post-#205 lever.

**R4 — ⚪ the lane-band-source A/B (SLOT-234) is a RATE trade, not a seeding change — keep the DEFAULT lossless, and if a lossy variant is chosen, RE-TRAIN against the decode band.**
- Where: byte-close default is `serialize_lane_band_rd` (LBND2, per-frame quantized) — decode rebuilds the SAME per-frame lines (`levelset_byte_close_and_eval.py:1316,1024-1034`), so train==decode by default. The lossy `coherent_slot_{rpca,sort_MA}` variants (`analytic_lane_render_band.py:1471-1550`) DIVERGE the decode band from the GT-fit training band.
- Deep-math / NO-FAKE: if a smoothed variant is shipped for rate, the witness is trained to complement a band it will NOT see at decode — the **same train/decode-mismatch class that DISQUALIFIED AA-supersample** (§5b delta-1). The `per_dim_lambda` task-λ seam (edge-preserving on ∂d_seg/∂coeff, NOT geometric RMS) is the only smoothing that can save rate without a d_seg-through-R cost. Action: keep `coherent_slot_none` (lossless) default; make ANY lossy A/B measure d_seg-through-R on the ACTUAL decode-reconstructed band, never the GT band.

**R5 — 🟡 pose warm-start s_r/pitch (D): $0 improvement to the warm-start, low leverage.**
- Seed s_r from a fixed geometric rotation scale (not 0) and pitch from the vanishing-point/`liveCalibration` so ξ_stored starts closer to the PoseNet target → dξ has less to learn → faster d_pose convergence. Low leverage (dξ already closes it via rank-6), a nice-to-have.

## 4. VERDICT on the unification (explicit, per the operator's ask)

**Is the unification (one world-model both axes) exploited, or left on the table?** It is **DESIGNED (the `ego_xi_trajectory` seam) but deliberately not wired as the #205 default — and that is the CORRECT, measurement-grounded call, not a left-on-table optimality.** The two payoffs the unification would buy are both foreclosed by MEASUREMENT: (1) using ξ to CODE lanes is REFUTED (rate, swap-light clip); (2) using openpilot-ego to warm-start pose is DOMINATED by the PoseNet-target prior already in use. So there is **no large d_seg/d_pose lever hiding in "fuse the two priors into one ξ."** The genuine deep-math design that IS left on the table is narrower and geometry-level: **the three seeding paths independently roll (and inconsistently calibrate) their ground plane** — the measured horizon suboptimality (R1) and the 1.2-vs-1.22 plane split (R2) are the real, small, measured-backed levers. The one speculative unmeasured unification use — a ξ-driven partition temporal-consistency d_seg regularizer (the "third dual-use") — is a post-#205 research item, not a config change, and is likely dominated by the persistence/amplify levers already engaged (the measured erasure is spectral-bias, not temporal-flicker). **Honest bottom line: the seeding is well-engineered; do NOT chase more unification for #205 — chase R1 (the measured horizon fix).**
